# Тест-кейсы и распределение по пирамиде

## Новые тест-кейсы

Все суммы указаны в копейках. Шаг за границу равен 1 копейке. Для каждого кейса подготовить отдельные данные. Повторы одного запроса указаны в шагах.

Базовая карта: BIN `400000`, держатель `KAMILA BULGAKOVA`, валюта `643`, статус `ACTIVE`, баланс `100000`, дневной лимит `50000`, месячный лимит `200000`. Срок действия не истёк, использованные лимиты равны нулю. PAN получить из ответа создания карты. Другие суммы указаны в самих кейсах.

Базовый платёж: `mti=0100`, уникальный шестизначный `stan`, PAN тестовой карты, `processingCode=000000`, `amount=10000`, `currencyCode=643`, текущее время UTC в `transmissionDateTime`, `terminalId=TERM0001`, `terminalType=POS`, `merchantId=MERCH0000000001`, `mcc=5411`, `acquirerId=ACQ001`. Switch добавляет `issuerId=ISS001`. Для прямого вызова валидатора задать issuerId в объекте запроса. Для e2e подготовить мерчанта и терминал в тестовых данных.

В unit вызвать методы с заглушками зависимостей. В api проверить HTTP-контракт Card Management. В integration использовать реальные зависимости из предусловия. Для e2e поднять Gateway, Switch, Authorization, Card Management, BIN Lookup, Merchant Acquirer, RabbitMQ, Logger и PostgreSQL.

Асинхронный результат проверять опросом раз в 500 мс до 15 секунд, если в кейсе не указан другой срок. Это время ожидания теста, а не гарантия доставки. Искать операцию по отдельному PAN и сверять её поля. Фильтра по STAN в API поиска нет.

### Выбор уровней

| Кейсы | Почему выбран этот уровень |
|---|---|
| TC-P3-01, 02, 03, 04, 12 | Проверяются методы и решения на заданных данных. Достаточно объектов в памяти и заглушок |
| TC-P3-05, 06 | Проверяется HTTP-контракт одного сервиса |
| TC-P3-07, 08 | Проверяется сохранение и SQL в реальном PostgreSQL |
| TC-P3-09, 10, 11, 13, 14 | Нужны реальные брокер, слушатели или outbox. Соседние сервисы, не относящиеся к проверке, можно заменить заглушками |
| TC-P3-15, 16 | Проверяется весь путь платежа, баланс и запись в Logger |

### Ограничения реализации

- В TC-P3-11 описан ожидаемый таймаут confirm и reversal. В `LoggerClient` нет ожидания подтверждения, а `AuthorizationClient` использует отдельный `/rollback`. Эта ветка пока не реализована. TC-P3-12 проверяет существующее решение об откате при ошибке отправки.
- В TC-P3-13 ожидаются три попытки обработки и DLQ. В конфигурации есть `x-max-delivery=3`, но нет настройки retry потребителя. TTL DLQ проверяется отдельно в TC-P3-14.
- `AuthServiceImpl.rollback()` возвращает баланс, но не восстанавливает `limit_usage`.
- В TC-P3-15 ожидается `mti=0110` из API-контракта. `AuthorizationResponse.approved()` копирует `mti` запроса и возвращает `0100`. Gateway и Switch это поле не меняют.

## Распределение тест-кейсов практики 2

### Объяснение

Большую долю api / integration дали старые кейсы с запущенными сервисами и проверками сохранённых данных. Новые интеграционные кейсы проверяют SQL, RabbitMQ, outbox, подтверждения и DLQ. Заглушки не проверят реальные настройки брокера и запись в БД.

Unit-кейсов меньше, потому что исходные проверки Authorization описаны с реальным Card Management. На unit я вынесла новые проверки валидации, BIN, границ баланса и решения об откате.

В E2E я оставила успешный платёж и отказ заблокированной карте. Перекоса в E2E нет: 2 из 89 кейсов. Детали очередей проверяются на integration, где проще определить причину ошибки.

Из 75 кейсов среднего уровня 21 относится к api и 54 к integration. Контрактные проверки есть, но они сосредоточены на Card Management. Для остальных API отдельных проверок ошибок мало. Большое число похожих кейсов не доказывает полноту покрытия.
