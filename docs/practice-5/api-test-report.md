Для известного ограничения в таблице указано, чем оно обусловлено и что нужно учитывать клиенту. Тест на расхождение проходит, когда исходная версия воспроизводит описанное в таблице поведение.

## 5. Обоснование достаточности

- Для бизнес-отказов с доменным ответом проверяются HTTP-статус, код и причина. Разные условия могут давать один код, например `05` для заблокированной и неактивной карты. При остановке PostgreSQL проверяется общий 500 от Authorization и отсутствие кода и причины (§4).
- При проверке отдельного поля меняется одно значение за запрос. Отдельные сценарии проверяют зависимые поля, например порядок дат и взаимоисключающие селекторы массового обновления. Для пустого PAN в теле отката Card Management возвращает одно из двух сообщений, порядок не задан. Для фильтров используются совпадающие и контрольные записи и попарные сочетания параметров. Для карт проверяются состав, размер страницы и отсутствие дублей, поскольку порядок не задан. Для транзакций проверяется также порядок выдачи.
- Экспорт CSV проверяется на двух подходящих записях и одной контрольной. Тест проверяет содержимое, порядок строк, заголовки и поведение при передаче `limit` и `offset`. Ограничение экспорта в 50 000 строк потребует отдельной фикстуры такого размера.
- При повторе с тем же UUID и телом Logger возвращает исходную запись. Если сумма отличается, ожидается 409, а исходная запись сохраняется. Сквозной тест ждёт появления операции из Gateway в поиске. При отказе RabbitMQ тест проверяет восстановление баланса и отсутствие записи в течение пяти секунд после контрольной доставки.
- Вызов Switch без PAN выполняется после остальных фаз, перед удалением тестового стенда. Так повторная доставка записи с пустым PAN не влияет на сквозную проверку и сценарий восстановления RabbitMQ.
- Тесты создают карты и регистрируют тестовые BIN в Card Management через API. Фикстуры удаляют эти данные в `@AfterEach`. Записи Logger изолированы по идентификаторам. API удаления для них отсутствует, поэтому их удаляют вместе с томом стенда после каждого прогона.
- Область проверки ограничена HTTP-контрактами. API управления BIN в Card Management используется для подготовки и очистки данных. UI, WebSocket, прямые проверки БД и очереди RabbitMQ остаются вне задания. В фазах отказа проверяются HTTP-ответы системы.

## 7. Порядок запуска

Команды выполняются из корня репозитория при запущенном Docker с Docker Compose. Требуется PowerShell 7.4 или новее.

```powershell
pwsh -NoProfile -File ./scripts/run-api-tests.ps1
```

Для трёх последовательных прогонов.

```powershell
pwsh -NoProfile -File ./scripts/run-api-tests.ps1 -Runs 3
```
